Tier 3: two knobs, one wire format, and a benchmark that was lying about saturation

The largest number in this report required no code at all. Sweeping WORKER_CONCURRENCY and INGEST_BATCH_SIZE together — they interact, and sweeping either alone gets the wrong answer — found +142% of write throughput sitting in two environment variables. The code change that follows, enqueueing one stream entry per envelope instead of one per item, cuts stream entries by 90% and edge latency by 13%, and only shows its real value past capacity, where the old shape loses 21% of accepted events to a silent trim and the new one loses 0.0%. Getting there meant fixing the measurement twice: the “saturated” point was not saturated, and a flat 25% “loss” turned out to be an item-mix accounting error.

01What changed

Two defaults, one wire format, one round-trip cut — and two repairs to things the wire-format change quietly broke.

  • New defaults. WORKER_CONCURRENCY 4 → 8 and INGEST_BATCH_SIZE 50 → 200. Both dated from a write path that no longer exists: 50 was chosen when one entry was one statement, and 4 was last measured when an item cost ~10 transactions.
  • One stream entry per envelope. The edge built an IngestJob per item, each carrying its own copy of the tenancy ids, release, ip, user agent, sdk block and the unbounded context map. At 15 items per envelope that is 15 copies serialized, stored, read back and parsed for something the envelope stated once. The worker expands an IngestBatch back into per-item jobs, so nothing past the decode changed.
  • The edge, from four sequential Redis waits to two. INCR key limit → GET dsn cache → INCR app limit → XADD, each waiting on the one before it because it needed its answer. A process-local cache in front of resolve_env removes the middle wait and makes the app id known before the second limiter, so both counters go out in one pipeline.
  • The bind-parameter ceiling, which the fold silently broke. insert_into(…).values(&rows) binds every column of every row, and Postgres refuses past 65,535 parameters. That was unreachable while one entry meant one item, because INGEST_BATCH_SIZE capped both. An entry may now carry up to 1,000 items, so 200 entries is up to 200,000 rows. The inserts chunk internally, inside the same transaction, so it is still one commit however many statements it takes.
  • The batch is bounded in ITEMS, not entries. This one was found by the benchmark, not by reading. INGEST_BATCH_SIZE counts entries, and while an entry was an item that was also an item bound. Folding an envelope into one entry quietly multiplied the batch by the envelope size: at twice capacity, peak resident memory went from 214 MB to 2,164 MB — tenfold, from a knob nobody touched, on a workload nobody changed. INGEST_BATCH_ITEMS (default 1,000) is now the budget, and each worker converts it into an entry count using a moving average of the envelope size it has actually been seeing. That brought the same run back to 833 MB with the throughput intact.
  • MAXLEN is configurable. It was a literal at the call site — a data-loss control with no way to buy headroom. Default unchanged; INGEST_STREAM_MAXLEN now raises it.

Read the batch-50 column downward. Going from 4 workers to 16 makes throughput -22% — worse. A one-dimensional sweep of WORKER_CONCURRENCY at the shipped batch size would have concluded that the concurrency knob was already at its optimum and moved on. It is only at a batch size nobody had changed that the concurrency knob does anything at all, because with 50-entry batches the workers spend their time contending on commits rather than amortizing them.

The highlighted cell is what ships, and it is not the largest number in the table. 4 of the nine points land within 1.6% of each other at the top, which is noise — and all of them are demand-limited, because 19,029 items/s is the offered rate (19,199 items/s). Every one of them absorbed everything it was given, so the honest reading is “these four are indistinguishable” rather than “this one won”, and +142% is a floor on the gap, not a measurement of a ceiling. What separates them is the third column of each cell: 8 workers at a batch of 200 does it in 184 MB where 16/500 needs 405 MB. Same throughput, less than half the memory.

Each cell is also a single 60 s run, which justifies changing a default and not much more.

03Two corrections to the measurement, before any result

The saturated point was not saturated. The first matrix offered 1,600 req/s and reported both builds writing an identical ~19,000 items/s. That looked like a null result for the code change. It was: at the new defaults both builds wrote 100% of every countable item, so the row was measuring the load generator. A third arm at 3,200 req/s (§05) is the one that actually exceeds capacity.

A flat 25% “loss” that never happened. The loader compared crebain’s total item count against rows in error_events, analytics_events and transactions, and reported 25.2% of accepted items missing. The figure was identical to three significant figures across both builds and all six runs — which is the tell. total includes breadcrumb batches and identify() calls, neither of which writes a row to any of those three tables. Comparing like with like, the shortfall is exactly zero. A loss number that does not move when the build does is not measuring the build.

And a drain phase, so backlog and loss can be told apart. crebain used to tear the ingest down the instant the last request was sent. Anything still queued then counted as never written — indistinguishable from an entry Redis had trimmed away. --drain-secs holds the ingest open afterwards; every loss figure below is measured after the worker was given time to finish.

06What this cost

  • Revocation is no longer instant. Rotating a key, disabling an app or deleting an environment all DEL the Redis cache entry today, so the next request re-resolves. A process-local copy cannot be invalidated that way: a revoked key keeps ingesting on each replica for up to the cache TTL. The default is 5 s and INGEST_DSN_CACHE_SECS=0 disables the cache entirely — the pipelined limiter still applies, so that setting costs one round trip, not the change. Only positive results are cached in process; unknown keys still go to Redis, whose negative cache is what keeps them off Postgres.
  • An envelope is now all-or-nothing. A single unserializable item used to be skipped while its neighbours landed. The hole is narrower than it sounds — every field came from JSON that parsed moments earlier, and JSON that parsed cannot produce the map keys or non-finite floats that make to_string fail — and the answer, accepted: 0 and an SDK retry, is correct if it ever does.
  • Memory is now a budget rather than an accident. The ingest holds more at over-capacity than it used to — 217 MB against 833 MB — because it is holding a real backlog instead of letting Redis throw a fifth of it away. That is a choice, and it has a dial: INGEST_BATCH_ITEMS=200 reproduces the old footprint at the old throughput.
  • The ack owes a whole entry now. One entry carries many items, so acking on the first would retire it while its siblings were still unwritten — a crash there would be silent partial loss. The ack moved to the last item of each entry, and a failing item writes to the dead-letter queue without acking. A crash mid-entry therefore replays the envelope: duplicate writes rather than a silent hole, which is the trade the rest of this worker already makes.

07Verification

The equivalence test — the same signals written per-item and as a batch, then every row, counter and timestamp compared — still passes unchanged; the fold happens before it, at the decode. What is new is the pair of tests that pin the wire format on both sides of a deploy: the current shape must not parse as a legacy single-item job (it would silently lose every item but the first) and the legacy shape must not parse as the current one (it would dead-letter real, already-accepted telemetry, permanently — the DLQ has no reaper). The worker tries the current shape and falls back, so those two assertions are what make the fallback unambiguous rather than lucky.

08What is still on the table

  • A backlog metric, and an alert. Still the highest-value item and still not done. §05 shows the failure is reachable in sixty seconds of ordinary overload, and raising INGEST_STREAM_MAXLEN moves the cliff without removing it. The metric must come from stream offsets — XLEN counts acked-but-untrimmed entries and reads near the cap regardless.
  • The new defaults were swept on the pre-fold build. 8 workers and a 200-entry ceiling were measured when an entry was an item. The item budget makes the ceiling mostly moot, but the pair deserves re-sweeping on the folded wire format before anyone treats 1,000 items as optimal rather than merely safe.
  • The sweep is one run per point. It justifies the new defaults; the exact optimum deserves repeats, and the top group is demand-limited rather than measured.
  • The lifecycle and identify tails are still per-item — genuinely rare, and the lifecycle path is an ordered state machine rather than a commutative counter, so it is not a like-for-like fold.
