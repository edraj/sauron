The two isolating rows are the point: batching on its own accounts for essentially all of it. LTO on its own moves throughput by a quarter, and for a reason worth naming — it made the old path fractionally quicker at losing a race it was always going to lose.

02The thing that was actually in the way

Batching alone, measured first, made throughput worse — about a quarter of the per-item path. Postgres explained why:

ERROR:  deadlock detected
DETAIL: Process A: UPDATE issues SET users_seen = t.n FROM unnest(...)
        Process B: INSERT INTO "issues" ... ON CONFLICT ("app_id","fingerprint") DO UPDATE

Two statements on the same rows, one ordering its locks by (app_id, fingerprint) and the other by id. No sort order reconciles those. Under eight workers nearly every batch lost the race, rolled back, and replayed item by item — doing the work twice and reporting success.

This was in the baseline too. The 350 items/s measured on 3 August was largely this, not the insert count.

Why nobody had seen it

crebain's harness sent the ingest's stdout to /dev/null, and tracing_subscriber writes there by default. Every warning the ingest emitted during an isolated benchmark run — for the whole life of the tool — was discarded. A write path failing on every single batch looked, from outside, exactly like one that worked: rows still landed, crebain still reported 100% accepted and zero errors.

Deadlocks self-heal, which is what made this survivable and invisible at the same time. The harness now inherits stdout.

users_seen is a HyperLogLog estimate whose authoritative copy lives in Redis; Postgres keeps a denormalized copy so the Issues page can sort by it. It now writes only when PFADD reports the estimate actually moved, and at most once per issue per five seconds. Redis stays exact and immediate. Both write paths got the fix.

05Where the ceiling went

The wall/CPU split is the interesting part. One codegen unit per crate cannot spread across 20 cores, so the final link serializes: less total work on a longer critical path. On a shared CI runner the CPU number is the one that matters; on a laptop, the wall number is.

Worth knowing separately: packaging/rpm/sauron.spec appended -Ccodegen-units=16 to RUSTFLAGS, and RUSTFLAGS beats the profile. Setting codegen-units = 1 in Cargo.toml alone would have been a no-op for every RPM ever built. That override is gone, so packaged binaries now match what is measured here.

09A correction to the previous report

The 3 August page reported a “Redis backlog” of 480,648 entries growing linearly, taken from XLEN. That was wrong. XACK does not remove entries from a stream — only MAXLEN trimming does — so XLEN measures retained stream length, not unprocessed work. It reads about 480,000 in every run here, including the ones that drain completely.

The conclusion it supported still holds, because it never rested on that number: rows-written-versus-offered is the sound measure, and it said the same thing. Backlog has been dropped from this report rather than restated.

10What would undercut these numbers

  • The generator makes 5 fingerprints and 1 device key for 5,000 users. That concentrates contention onto a handful of rows far harder than real traffic would. It is what exposed the deadlock — useful — but it also means the batched path's advantage here is, if anything, understated: the folding it does is worth more when a batch spans many distinct sessions and devices.
  • Postgres, Redis and the load generator share one box (load average ~4 from unrelated containers). Absolute figures are pessimistic; the ratios are sound because every run paid the same tax.
  • Both 4,083 rps batched runs saturated, so the LTO-on-batching throughput comparison reads 0% and means “could not be measured here”, not “no effect”. The CPU-per-item row is the one to read.
  • Batch size 50 was inherited, not chosen. It was the XREADGROUP count from when entries were written individually. It is now INGEST_BATCH_SIZE and is the largest untuned lever left.

11Reproducing this

INGEST_BATCH_WRITES=0|1   # per-item or batched, same binary
INGEST_BATCH_SIZE=50      # entries per XREADGROUP, and per batched write
WORKER_CONCURRENCY=8 INGEST_DB_POOL=8

cargo test -p sauron-pipeline          # incl. the batch/per-item equivalence test
cargo bench -p sauron-core --bench json_tax
scratchpad/drive2.sh <tag> <build-dir> <batch 0|1> 4000 60

Hold offered rate, duration and worker count fixed, then diff three numbers: items/s written, transactions per item, and CPU-seconds per 1,000 items. Do not compare accepted req/s — it was never the constraint, and at these rates it is the generator's limit rather than the server's.
