Tier 2: the cliff the benchmark could not see

Two edits: fold the per-item workflow upserts into one statement, and stop the edge waiting once per envelope item for Redis. Neither could be measured first, because the load generator emitted no workflows at all and two-item envelopes — so three previous reports scored a workload in which both changes were structurally invisible. Fixing the instrument first, the fold is worth +157% of write throughput at the shipped default. And a sweep that changes no code at all found +64% sitting in an environment variable. Checking this round’s numbers also turned up a defect in the benchmark harness that invalidates the CPU and memory rows of all three previous reports.

01What changed

Two edits to the product, and one to the thing that measures it.

  • The workflow fold. batch.rs stage 7 replayed repo::bump_workflow once per item carrying a workflow tag — one statement, and because diesel-async runs outside an explicit transaction, one commit and one round trip each. For an app that tags its traffic, the batched write path amortized everything else and then paid batch_size single-row upserts anyway. Now folded by (app_id, workflow_id) and written as one unnest upsert.
  • The edge’s XADDs. sauron-ingest enqueued one item per XADD, awaiting each. A 16-item envelope paid 16 sequential network waits for commands that were always issued back-to-back with nothing decided in between. Now one pipelined round trip.
  • The instrument. crebain gained --workflow-ratio and --batch-items. Both default to today’s behaviour, so old benchmark commands reproduce old workloads.

02Why the previous three reports could not have found this

The generator hardcoded workflow_id: None on every item it built, and shipped envelopes of one or two items. So the per-item workflow upsert never executed during a benchmark, and the edge never enqueued enough items in one request for the round trips to matter.

That is a specific and repeatable failure: a load generator that does not generate a signal makes the code handling that signal invisible, not merely under-weighted. Nothing in the previous reports was wrong — they measured what they drove. They just could not have found this, and neither could any amount of re-reading the numbers.

The measurement had to come before the optimisation

The order here was: teach the generator to produce the traffic, confirm the traffic lands (22,030 workflow rows in a smoke run, 16 items per envelope), and only then measure. Had the edits landed first, the benchmark would have reported a clean 0% and both would have looked worthless.

03The free +64%: a config sweep, no code

INGEST_BATCH_SIZE is env-overridable and has sat at 50 since before the batched write path existed, when it only bounded how long a worker went between Redis reads. Under batching it is the amortization factor for every statement. Swept on the before build:

06A correction to the previous three reports

While checking this round’s numbers, the CPU column came back as exactly zero against 3.3 MB of resident memory — which is not a plausible server, it is a bash process. The harness had been resolving the process to sample with:

INGEST_PID=$(pgrep -f "$INGEST_BIN" | head -1)

That path string also appears in this script’s own argv, in the wrapper shell’s, and in crebain’s — crebain is launched with --ingest-bin <path>. pgrep lists ascending by pid, and crebain is the parent that spawns the ingest, so its pid always sorted first. The CPU and RSS columns of reports 1–3 measured the load generator.

Sampling both processes at once shows they are nowhere near interchangeable:

at 800 req/sCPU-speak RSS
ingest (what was wanted)23.359.9 MB
crebain (what was measured)5.415.6 MB

Resolution is now by executable — pgrep -x plus a readlink /proc/<pid>/exe comparison, which is also what distinguishes the before build from the after build when both binaries share a filename — and the harness aborts the run if it resolves to nothing, because an all-zero CPU column is indistinguishable from an infinitely fast server. crebain is now sampled into its own columns so the two can never be silently swapped again.

What survives: every throughput, round-trip, commit and row-count figure in those reports, which came from Postgres and Redis rather than from /proc. That includes the soak’s central finding of silently trimmed events. What does not: their CPU-per-event and RSS rows. The soak’s “RSS 45 MB → 461 MB” was crebain’s memory — in-flight requests piling up in the client as the server slowed, which is a symptom of the collapse rather than evidence about its cause.

07Verification

The existing equivalence test drives the same signals through process_job (per-item) and process_batch (folded) into two apps and compares what lands. It covered issues, sessions, devices and event_users — not workflows, which is exactly the table this round moved into the batched path.

It now does, and the fixture was built around one specific trap. The conflict arm reads COALESCE(workflows.session_id, EXCLUDED.session_id) — the row’s existing value first — so under sequential upserts the first non-null value sticks. The session fold next to it is written COALESCE(EXCLUDED.x, sessions.x), where the last wins. A fold copied from its neighbour would be wrong in a way no counter, timestamp or row count would reveal. The fixture puts a workflow’s first signal on one session and its later signals on another, and pins the result.

cargo test -p sauron-pipeline   16 passed   (2.56s, both TEST_ URLs set)
cargo test -p sauron-redis       3 passed   (0.24s)
cargo clippy --workspace --all-targets   clean

The timings matter: a run of this suite that finishes in 0.00 s is one where the database-backed tests silently skipped on unset TEST_DATABASE_URL/TEST_REDIS_URL while still printing ok.

08What is still on the table

  • A backlog metric, and an alert. Still the highest-value item and still not done. MAXLEN ~1,000,000 is hardcoded at the xadd_job call site, and every saturated run in this report crossed it — Redis trimmed unread entries while the edge went on truthfully reporting 100% accepted. Must be derived from stream offsets; XLEN reads near the cap regardless.
  • One stream entry per envelope. Every item re-serializes the whole shared header — ids, release, ip, user agent, sdk, and the full context blob. At 15 items per envelope that is 15 copies into Redis and 15 parses back out. The largest byte-level win left, and a wire-format change.
  • Ship a better INGEST_BATCH_SIZE default. The sweep above is one run per point; it justifies a change but the exact value deserves repeats.
  • The lifecycle and identify tails are still per-item. They are genuinely rare, unlike the workflow bumps, and the lifecycle path is an ordered state machine rather than a commutative counter — not a like-for-like fold.
