Latencies are the p50 of two samples against the exact URLs the dashboard fires, with the production environment selected where the dashboard does so. "timeout" is the API's 60 s request budget, which a reverse proxy surfaces as 504.

What was wrong

  • The fast paths never switched on. Every analytics page has a rollup-served shape, but each is gated on a per-app marker only an operator's sauron-migrate backfill-* could write. No package, unit or compose step runs it, so an upgraded deployment stays on the legacy O(history) queries: the Users page's three calls, device-groups and counts each crossed 60 s, screens and journeys took 26–42 s.
  • Timed-out requests kept running. The request layer answered 503 at 60 s but Postgres finished the abandoned statement anyway (device-groups ran 182 s more), holding its pool slot. A few reloads filled all 16 slots, and cheap endpoints failed too, which is why "most APIs" failed rather than a handful.
  • The Devices list had no rollup path at all. Environment-scoped, it ran four unbounded EXISTS and four LATERALs per device before paging, then a three-table UNION per device that opened 344 partition scans each.

What changed

  • sauron-ingest now runs all four backfills itself on start-up and on each daily pass while any gate is closed, under a session advisory lock, cheapest gates first. The event backfill records its cursor in the same transaction as each day, so an interruption resumes instead of double-counting (ROLLUP_AUTO_BACKFILL=0 opts out; the migrate commands still work).
  • The API's request pool carries a server-side statement_timeout one second under the request budget; detached cache recomputes and reapers use a separate unbounded pool. A cancelled statement answers 503 query_timeout instead of a bare 503.
  • The Devices list reads device_environments and device_sessions_daily once backfilled, pages before probing the latest distinct id, and bounds that probe to the partitions around the device's known last activity.
  • The freshness chip says "Building history · n/N days" while the gate is closed, so a slow page explains itself.

Still open

The env-scoped Exceptions list (2.9 s) and stats (0.7 s) have no rollup: the page enriches each listed issue with an all-time count(*), count(DISTINCT user) and newest-event probe over its error events in that environment, so cost scales with events per issue. A per-issue, per-environment daily rollup would bring it to milliseconds; it is a separate slice.
