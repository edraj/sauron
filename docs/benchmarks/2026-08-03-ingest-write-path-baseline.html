What the two numbers actually mean

A 202 from the ingest edge means the item was XADD-ed to Redis — not that it reached Postgres. The worker pool drains that stream asynchronously, so crebain's summary can report a flawless run while the write path falls steadily further behind.

Accepted at the edge — what crebain reports 8,083 items/s
Written to Postgres — sampled from row counts 350 items/s

Bars are to scale. Counting only row-producing signals (errors, events, transactions), 6,000 items/s were offered and 350 landed. The write path runs 17× underwater. crebain's verdict on the same run was 244,984 accepted · 100.0% · p99 2.15 ms · 0 errors.

Adding workers stops helping almost immediately

WORKER_CONCURRENCY and the connection pool have to move together — the pool was hardcoded to 8 in sauron-ingest/src/main.rs, exactly matching the 8 workers, so raising one alone did nothing. With both swept:

What the sweep rules out

From 8 to 64 workers, tup_fetched grew 7× while rows written grew 1.66×. Extra workers buy repeated lookups, not throughput. Removing error and issue items entirely only reached 606 items/s, so row contention on the issues table is not the dominant limit either — the ceiling is the ~10 sequential, unbatched round-trips each event costs.

Why SIMD would not help

The process holds 0.89 of 20 cores and does not move when worker count changes 8×. JSON is 14.2 µs against a ~23 ms per-item wall — six hundredths of one percent. lto=fat makes the JSON 8% faster and the throughput no faster at all. There is no CPU here to reclaim; the time is spent waiting on Postgres.

Read these before comparing

  • Postgres, Redis and the load generator all ran on the same box, with unrelated containers pushing load average to ~4.3. Absolute numbers are pessimistic; ratios are sound.
  • crebain's generator emits only 5 distinct fingerprints, so all errors contend on 5 issues rows — more contention than production. The events-only run brackets that effect at roughly 13%.
  • The 350 items/s figure counts errors, events and transactions. The 5,000 identifies are a one-shot burst at start and are excluded from the steady-state rate but included in the transactions-per-event ratio.
  • Each run used a fresh ephemeral database, so pg_stat_database covers exactly that run with no delta arithmetic.
  • perf is unavailable on this box (perf_event_paranoid=2), so CPU attribution is the microbench-to-wall-clock ratio rather than a sampled profile.

Reproducing this run

The driver samples what crebain cannot see: Postgres row counts, stream length and process CPU, once a second for the duration of the run. 

cargo build --release -p sauron-ingest -p crebain

# end-to-end: writes <tag>.samples.csv, <tag>.pgstat, <tag>.html
WORKER_CONCURRENCY=8 INGEST_DB_POOL=8 ./drive.sh 4000 60 baseline

# per-item CPU
cargo bench -p sauron-core --bench json_tax

To compare a later run, hold the offered rate (4000) and duration (60) fixed and diff three numbers: items/s written, final backlog, and transactions per event. Throughput at the edge is not a useful comparison — it was never the constraint.

Scaffolding for this baseline is uncommitted in the working tree: crates/sauron-core/benches/json_tax.rs, the INGEST_DB_POOL override in bins/sauron-ingest/src/main.rs, and the environment pass-through in bins/crebain/src/harness.rs.
