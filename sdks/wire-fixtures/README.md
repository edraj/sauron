# SDK wire fixtures

One file per SDK, each holding **one envelope that the SDK itself produced** — captured
off its own transport (the fake `fetch` / `HttpMessageHandler` / sender the SDK test
suites already use), not hand-written.

They exist so the backend can prove, without any JS/Python/Dart/.NET toolchain, that
what the SDKs emit actually **deserializes into the real wire type**
(`backend/crates/sauron-core/src/envelope.rs`). That test is
`backend/crates/sauron-core/tests/sdk_wire_conformance.rs`:

```
cargo test -p sauron-core --test sdk_wire_conformance
```

Before these fixtures existed, every SDK suite asserted its envelope matched a
hand-written golden **literal in the same repo** — so an item shape that the backend's
`serde` rejects outright (a non-`Option` field sent as `null`) passed every SDK test and
every backend test simultaneously. The envelope is all-or-nothing: one invalid item is a
400 for the whole batch, and every SDK classifies 400 as a non-retryable drop.

## Regenerating

Each fixture is rewritten by that SDK's own suite, so a normal test run keeps it fresh.
Note that these are **tracked files a test writes to**: running the suite overwrites
`<sdk>.json` in the working tree every time. That is only tolerable because the bytes
come out identical (see below), so `git status` stays clean — if it ever does not, the
normalizer is the thing to fix.

| Fixture | Regenerated by | Command (from the SDK dir) |
|---|---|---|
| `js.json` | `sdks/js/test/wire-fixture.test.ts` | `npx vitest run` |
| `node.json` | `sdks/node/test/wire-fixture.test.ts` | `npx vitest run` |
| `python.json` | `sdks/python/tests/test_wire_fixture.py` | `python3 -m pytest` |
| `csharp.json` | `sdks/csharp/Sauron.Tests/WireFixtureTests.cs` | `dotnet test` |
| `flutter.json` | `sdks/flutter/test/wire_fixture_test.dart` | `flutter test` |

A regenerated fixture must come out **byte-identical**. Regeneration is a no-op, not a
diff, and CI enforces that: every `sdk-*` job runs
`.github/scripts/check-wire-fixture.sh <sdk>` after its suite and fails if the file
moved.

So when a diff does appear, it is one of exactly two things:

1. **The wire shape changed.** Review it like a schema change, commit the regenerated
   fixture, and expect `sdk_wire_conformance` to have an opinion about the new shape.
2. **The normalizer has a hole** — the file picked up something the toolchain supplies
   rather than something the SDK decided. Then the fix is the normalizer, *not*
   committing the noise. A gate that fires for non-reasons is worse than no gate: it
   teaches reviewers to approve fixture diffs unread, which is exactly how a wire
   regression gets through a passing conformance test.

## Normalization

Each SDK's IO helper (`sdks/js/test/wire-fixture-io.ts` and its four siblings) pins two
categories.

**Intrinsically dynamic:** `timestamp` / `sent_at`, `event_id`, `session_id`,
`device_id`, `workflow_id`, `lineno` / `colno`, `raw_stacktrace`, `build_id` /
`isolate_dso_base`.

**Toolchain- or host-derived** — added because it was making the files unreproducible:

| Pinned to | What it was |
|---|---|
| `function` → `<fn>`, `module` → `<module>`, `filename` / `abs_path` → `<file>` | stack-frame identity. Under vitest these were the runner's internals (`chunk-hooks.js`, `runSuite`, `processTicksAndRejections`); under `package:test`, `declarer.dart` / `invoker.dart`. A vitest or Dart SDK bump rewrote them with no wire change. |
| `context.os.name` / `.version`, `context.runtime.version`, `context.device.family` / `.model` / `.arch` → `<host>` | the host kernel string and the Node / CPython / .NET / Dart version. Different on every machine, and these three blocks are free-form `serde_json::Value` on the wire (`envelope.rs`), so their contents prove nothing about conformance. `context.runtime.name` is deliberately NOT pinned — it is an SDK constant. |

Everything else is untouched, and that is deliberate: the **item shape, key set,
nullability and the stack-frame COUNT are exactly what the SDK sent**. A `null` is never
replaced with a placeholder, because "this field arrived as `null` and still
deserialized" is part of what the fixture proves.

### The one thing still toolchain-shaped

Frame **count** — and whether a given frame's `function` arrived as a string or as
`null` — is not normalized, and where it comes from differs per ecosystem. Only three
of the five fixtures are runner-depth-shaped at all:

| Fixture | Frames | Where the depth comes from |
|---|---|---|
| `js.json` | 9 | vitest + Node internals above the `new TypeError(...)` — i.e. the runner's call stack |
| `node.json` | 9 (+ one 0-frame item) | same |
| `flutter.json` | 4 | `package:test` internals — same shape of exposure |
| `python.json` | **1** | the raised traceback, not the call stack: `capture_exception` reads `exc.__traceback__`, which starts at the `raise` inside the test's own `try` |
| `csharp.json` | **1** | same — `ex.StackTrace` begins at the `throw`, so xUnit's frames are not in it |

An earlier version of this section justified leaving frame count alone with "it is stable
for a given lockfile, so it does not vary between a developer's machine and CI (both
`npm ci`)". That reasoning only ever covered js and node. `sdks/python` declares
`test = ["pytest>=7"]` with **no lockfile** and CI installs whatever pytest is current;
the csharp job has no lockfile either. So the lockfile argument is unavailable for
exactly the two ecosystems it was implicitly claiming to cover.

The actual exposure is nil for those two, but for a different and better reason: their
frame count is **1**, taken from the raised exception rather than from the runner, so no
pytest or xUnit release can move it. Where the lockfile argument does apply — js and
node — it holds: both jobs `npm ci`, so a count change only accompanies a deliberate
dependency bump, where a fixture diff is expected and reviewable.

That leaves `flutter.json` as the one genuinely unpinned case: CI runs
`channel: stable` unpinned, so a Flutter release could move its 4 frames with no repo
change. See the note on that job in `.github/workflows/ci.yml`.
